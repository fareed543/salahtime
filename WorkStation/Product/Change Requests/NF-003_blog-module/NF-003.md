## 2. Goal & Acceptance Criteria

**Goal:** any logged-in user can write an SEO-ready article; an admin reviews
it in the back office and publishes, rejects with a reason, or proposes
improvements the author approves; every change is versioned and logged;
published articles are public, indexable and show their views; authors are
notified at each step and credited on an author page.

| # | Given / When / Then | Platform |
|---|---|---|
| AC-1 | A logged-in user opens **Write an article** (`/blog/write`) and fills title, content (headings, bold, italic, lists, links, quotes), category, tags, language, cover image + alt text, meta title, meta description, focus keyword, slug, references. A live **SEO score** (0–100) with a checklist updates as they type. **Save draft** keeps it private. | Web + Android |
| AC-2 | **Submit for review** needs title, ≥ 150 words, category and meta description. On submit the article becomes *Submitted* and the admin is emailed with a link to the back office. A user can have at most 3 articles waiting for review and submit at most 5 times a day. | Web + Android + API |
| AC-3 | Back office → **Blog** lists articles with status tabs (Submitted, Changes proposed, Published, Rejected, Drafts, All) and counts, search, SEO score and views. | Back office |
| AC-4 | On an article the admin sees the content preview, SEO checklist, author, versions and history, and can: **Approve & publish**; **Reject** (reason required); **Propose changes** (edit any field incl. SEO, with a note); **Unpublish**; **Restore** an older version as live. | Back office |
| AC-5 | Approve → article is public at `/blog/<slug>`; author gets an email ("Your article is published") with the link and a WhatsApp share link, and a push notification. Reject → author gets the reason by email and push and sees it in **My articles**. | API + Web + Android |
| AC-6 | Propose changes → status *Changes proposed*; author is emailed/pushed; in **My articles** they see each changed field side by side (current vs proposed) with the admin's note and **Accept & publish** / **Decline**. Accept publishes the proposed version; decline sends it back to *Submitted* with the author's note; the admin is emailed either way. | Web + Android + API |
| AC-7 | Every save by anyone creates a new numbered **version**; nothing is overwritten. Every action (created, saved, submitted, published, rejected, proposed, accepted, declined, unpublished, restored, view milestone) is logged with who, when, from → to status and note, shown as a timeline to the author and the admin. | All |
| AC-8 | Editing a published article creates a new version; the live version stays public until the new one is published. | All |
| AC-9 | `/blog` lists published articles (newest first, category filter, search); `/blog/<slug>` shows the article with author, date, reading time, views, cover, references; `/blog/author/<id>` lists an author's published articles and total views. All three are indexable with their own title/description/canonical; the article has `BlogPosting` JSON-LD; non-content pages (write, my articles) are `noindex`. | Web (+ Android) |
| AC-10 | Views count once per visitor per article per day; bots, the author and prerender are not counted. When an article passes 100 / 1,000 / 10,000 views the author is emailed and it is logged. | API |
| AC-11 | Published articles are in `sitemap-blog.xml` and prerendered at build time (same as masjid pages); unknown `/blog/<slug>` shows "not found". | Web build |
| AC-12 | Article HTML is cleaned on the server (allowed tags only, no scripts/styles/iframes, links get `rel="nofollow ugc"` unless internal). | API |

**Out of scope:** comments, reactions, images inside the article body (cover
image only), scheduled publishing, multilingual versions of one article,
"featured" / writer of the month, AI meta suggestions.

## 4. Design Delta

**Data**

- `bt_blog_article` — one row per article: `author_id`, `status`
  (`draft | submitted | changes_proposed | published | rejected`), `is_public`,
  `slug` (of the live version, unique), `live_version_id`, `latest_version_id`
  (author's working copy), `proposal_version_id` (pending admin proposal),
  `views`, `reject_reason`, `reviewed_by`, `submitted_at`, `published_at`,
  timestamps.
- `bt_blog_article_version` — immutable snapshot per save: `version_no`,
  `source` (`author | admin_proposal | admin_restore`), all content and SEO
  fields, `seo_score`, `word_count`, `note`, `created_by`, `created_at`.
- `bt_blog_article_event` — the timeline: `action`, `from_status`,
  `to_status`, `actor_id`, `actor_role`, `version_id`, `note`.
- `bt_blog_article_view` — unique `(article_id, view_date, visitor_hash)`;
  `bt_blog_article.views` is incremented only when a row is inserted.

**Status flow**

```
draft ──submit──▶ submitted ──approve──▶ published
  ▲                 │   ▲  └──reject──▶ rejected ──edit+submit──▶ submitted
  │                 │   └─────decline─────┐
  │                 └──propose──▶ changes_proposed ──accept──▶ published
published ──author edits──▶ draft (live version stays public) ──submit──▶ …
published ──unpublish──▶ is_public = 0 (status kept; republish = approve)
```

**SEO score (100 points)** — the same rules in `api/components/BlogSeo.php`
and `frontend/.../blog-seo-score.ts`: meta title 30–60 chars (10), meta
description 120–160 (10), focus keyword set (5), in title (10), in meta
description (5), in first paragraph (5), in slug (5), words ≥ 600 (15; ≥ 300 → 8),
has H2 subheadings (10), cover image (5), cover alt text (5), an internal link (5),
references (5), category + at least one tag (5). The stored score is the
server's.

**Notifications** — email via the branded template (same sender as
`SupportTicketMailer`); push to the author's registered devices via FCM
(skipped and logged when no key/token); in-app via **My articles** status,
reason and proposal.
