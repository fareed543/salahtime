## 1. Request

> Mostly for managing the sehri and iftar program — Masjid Members: all the users should appear under that masjid.
> Guest: registers; attractive profile page; profile updated with employment details; for the user, active programs within range appear on the Dashboard with an Enroll option.
> Volunteer: can manage the program, add the packets count, make users volunteers; can update the profile of any subscribed member (latest save wins).
> Admin (creator): manages the program, views members and their details, adds packets count, sees program stats, makes users volunteers.
> Gender captured at registration. Gents see only gents, ladies see only that masjid's ladies; only volunteers and admins see both.

Design approved 2026-11-09 with all 12 open questions as recommended (§ Open Questions).

## 2. Goal & Acceptance Criteria

**Goal:** a program's Admin and volunteers run sehri / iftar distribution end to end in the app, members join programs near them, and member lists stay gender-separated for everyone but the program team.

## 4. Design Delta

**FDS:** see the design page (roles table, flows A–F, gender rule). Rules:
- PRG-R1 Program roles: 1 Admin (creator / organiser), 2 Volunteer, 3 Subscriber. Super admin = `id_customer_type` 1.
- PRG-R2 Volunteer may: view members (both genders), add member, make volunteer / subscriber, enter packets, edit subscribed members' profiles, view stats. Not: edit / delete the program, remove a volunteer or the Admin.
- PRG-R3 Regular members see only same-gender members of the list, with name + photo.
- PRG-R4 Profile edits by the team: allowed while the member is enrolled and the program has not ended; last save wins; each changed field logged.
- PRG-R5 Near-me: program active, not ended, open to viewer's gender, any halqa masjid within `radius_km`.

**HLD:** one permission helper in `HttpRamadanController` (`programRoleOf`, `requireProgramTeam`) used by every program endpoint.

**LLD:** None (endpoint contracts in §5 code comments).

### Design change found in UI testing (2026-11-09, owner's direction)

The program form's Area dropdown listed only areas the user created, and the Area screen cannot add masjids, so a
new admin could not create a program and "Programs near you" could not place it
(`HttpRamadanController.php` `actionHalqaList`). Owner's direction: suggest areas that already exist, add what the
user types, no duplicate area names within a city; use the user's location for suggestions.

- `bt_halqa.id_city` (city from `bt_cities`), `latitude` / `longitude` (creator's location), unique key
  (`id_city`, `name`); existing duplicates merged — `database/2026-11-09_nf012_programs.sql` part 6.
- API `area-suggest` (nearest city to the user + areas within 25 km, nearest first, or by typed name in a city),
  `city-search`; `save-program` finds or creates the area from `area_name` + `id_city` (names compared ignoring case
  and extra spaces).
- "Programs near you" places an area by its masjid nearest the user, else its saved location, else its city centre.
- Frontend `community/programs/area-picker` replaces the Area dropdown; `AREA_PICKER.*` in all 13 languages.

## Open Questions / Follow-ups (all answered "as recommended", 2026-11-09)

1. Volunteer manages members, distribution, stats; not program edit / delete.
2. Volunteers can make volunteers; only the Admin removes one.
3. Range: 10 km default, per program `radius_km`.
4. Add member: account from name + mobile, no SMS.
5. Keep halqa (no single host masjid).
6. Employment status: Employed, Self-employed, Student, Not working, Retired.
7. Team (Admin + volunteers) sees full mobile; masked elsewhere.
8. Regular members see same-gender members lists (name + photo) on masjid and program pages.
9. Masjid owner sees both genders.
10. Existing users confirm gender once at next sign-in.
11. Program "Open to": Brothers / Sisters / Both.
12. Team profile edits only while enrolled and the program has not ended.
