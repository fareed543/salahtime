## 1. Request

"IN BO & FO — For Action Notifications we can use sweetalert, currently we are
showing text messages on the top of the form, it not appearing to the user."
(Screenshot: SweetAlert2 success popup "Good job! / You clicked the button! / OK".)

## 2. Goal & Acceptance Criteria

**Goal:** the result of every user action (save, submit, delete, send, upload,
sign in) is shown as a SweetAlert popup the user cannot miss, not as a text
banner at the top of the form.

| # | Given / When / Then | Platform |
|---|---|---|
| AC-1 | Given any screen in §3, when an action succeeds, then a green SweetAlert success shows the message; no inline success banner remains. | Web + Android (FO), Web (BO) |
| AC-2 | When an action fails (API error, offline, 429…), then a red SweetAlert error shows the API's message or the screen's fallback text; no inline action-error banner remains. | Web + Android (FO), Web (BO) |
| AC-3 | When a form is submitted with invalid fields, then a warning SweetAlert shows the summary ("Please correct the highlighted fields") and the per-field hints stay inline. | Web + Android (FO), Web (BO) |
| AC-4 | When an action is followed by navigation (sign-up → OTP, reset password → login, BO program save → detail, halqa delete → /area), the popup is still visible after the route change. | Web + Android (FO), Web (BO) |
| AC-5 | Page-load errors, field hints and status/instruction text (e.g. "OTP sent to …", report-issue thank-you screen, Qibla permission hint) stay inline exactly as today. | Web + Android (FO), Web (BO) |
| AC-6 | FO messages that are translation keys show translated text in the popup (all 13 languages, RTL for Arabic/Urdu). | Web + Android |
| AC-7 | On Android the popup is not hidden under the status bar / notch. | Android |

**Out of scope:** translating the hard-coded English FO auth strings (logged
as follow-up); replacing `window.confirm` prompts (`programs.component.ts:466`,
`masjid-gallery.component.ts:183`, `masjid-timing-history.component.ts:89`,
BO `app-versions/list.component.ts:61`); API changes.

## 4. Design Delta

**Rule (FDS, both apps) — `UX-NOTIFY-1`:** the outcome of a user action is
shown through the app's notify service; inline text is only for page-load
errors, field validation and instructions the user must keep reading.

| Kind | FO (`NotifyService`) | BO (`ToastService`) |
|---|---|---|
| Success | `success()` — toast, auto-close 3.5 s | `success()` |
| Error | `error()` — see Q1 | `error(err, fallback)` |
| Validation summary | `warning()` | `warning()` |

**HLD:** no new hats. Each converted component injects the existing service;
where one field served both load and action (`programs.error`,
`profile.message`, `blog-editor.message`, BO `program-details.errorMessage`),
the load case keeps the field and the action cases call the service. The
action banner `<div>` is removed from the template.

**FO `NotifyService`:** add a safe-area top offset for Android; no API change
unless Q1 picks the centered-popup option (then `error()` opens a centered
modal with an OK button instead of a toast — BO `ToastService.error` the same).

**LLD:** None.
